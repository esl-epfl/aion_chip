# Flow output

Everything the nine flow steps produce. One directory per step, numbered in
the order they run, each wiped and rewritten in full by the step that owns it:

```
synth.core        \
pnr.core           \  fixed FuseSoC handles on the directories below
rewrite.core       /
pnr_simple.core   /
aion_cells.core       handle on the cell models step 6 draws -- TRACKED, but
no_aion_cells.v       REGENERATED by step 6; the .v is its empty placeholder

coherence.json          what ran when, and whether it still adds up
logs/<step>/            one file per command the handler ran   (git-ignored)
1_synth/                synthesis + pre-PnR STA          (git-ignored)
2_pattern_extraction/   the mined AION cell library      (git-ignored)
3_rewrite/              the netlist that uses them       (git-ignored)
4_characterization/     SV + SPICE testbenches           (git-ignored)
5_gate_minimization/    one CMOS stack per cell          (git-ignored)
6_layout_drawing/       drawn cells and their views      (git-ignored)
7_pnr/                  the hardened chip                (git-ignored)
8_render/               PNGs of the die and its AION cells (git-ignored)
9_report/               AION vs the baseline: report.md,   (git-ignored)
                        report.json and a standalone report.html
pnr_simple/             the PDK-only baseline            (git-ignored)
                        not a step -- `make pnr_simple` builds it, and
                        step 9 is the only thing that reads it
```

The inputs live in `../implementation/`: the config template, the SDC, the pin
order, and `cells/`, where step 6 publishes the views step 7 places.

Run it with `./flow.py` (or `make flow`); see `../scripts/flow/README.md`.

## Why the .core files

The simulation targets in `aion.core` need to name a netlist, and the netlist
only exists after the flow has run. Each `.core` here is a FuseSoC core
pointing at a fixed path inside its directory, so `aion.core` can depend on
`epfl:aion:flow_pnr_simple:1.0.0` instead of hard-coding a path that may not
exist yet. Depend on one before its step has run and FuseSoC reports the
missing file; the Makefile checks for it first and says which step to run.

| Core                            | Files it points at                            | Produced by |
| ------------------------------- | --------------------------------------------- | ----------- |
| `epfl:aion:flow_synth:1.0.0`      | `1_synth/nl/tt_um_aion.nl.v`                | step 1 |
| `epfl:aion:flow_rewrite:1.0.0`    | `3_rewrite/nl/{aion_cells.v,tt_um_aion.nl.v}` | step 3 |
| `epfl:aion:flow_pnr:1.0.0`        | `7_pnr/nl/tt_um_aion.nl.v`                  | step 7 |
| `epfl:aion:flow_pnr_simple:1.0.0` | `pnr_simple/nl/tt_um_aion.nl.v`             | `make pnr_simple` |

`flow_rewrite` names two files on purpose: the netlist instantiates the AION
modules and nothing else declares them, so a simulator handed only the netlist
elaborates a design full of black boxes.

`nl/` is the logical netlist and the one to simulate. `pnl/` next to it is the
same netlist with the power pins connected (`VPWR`/`VGND`), which the PDK
simulation models do not declare — it is for LVS, not for simulation.

## What each directory holds

Steps 1 and 7 copy the `final/` views of the last LibreLane run, plus its logs
and every report, so their layout follows LibreLane's:

```
nl/        logical gate-level netlist
pnl/       powered netlist (LVS)
def/ odb/  placed-and-routed database
gds/       streamed-out layout
sdf/       one directory per corner, consumed by the post-PnR simulations
spef/      parasitics
lib/       timing model of the block itself
reports/   every .rpt of the run, flattened one level
logs/      flow.log and resolved.json
metrics.*  the run's metrics, csv and json
```

Both carry `sdf/`; only `7_pnr/` and `pnr_simple/` carry a placed database.

Steps 2 to 6 are the AION-specific half:

```
2_pattern_extraction/  aion_cells.v  aion_cells_elite.v
                       work/selection.json  report/pattern_report.json
3_rewrite/             nl/{aion_cells.v, tt_um_aion.nl.v}
                       report/rewrite_report.{json,md,html}
4_characterization/    steps/aion_char/tb/{sv,spice}/  gold_functions.md
                       steps/aion_char/tb/spice/reference_cells.spice
5_gate_minimization/   raw_spice/reference_<CELL>.spice
                       minimized_spice/<CELL>_minimized.spice
6_layout_drawing/      <CELL>/{<CELL>.gds, drc/, lvs/, pex/, char/,
                              baseline/, final/, <CELL>.compare.md}
```

`3_rewrite/nl/aion_cells.v` is the library of record: exactly the cells the
netlist instantiates. Steps 4, 5 and 6 all read that copy rather than step 2's
output, so a hand-curated selection propagates without being re-derived.

`logs/<step>/` holds one file per command the handler ran, tee'd live. It sits
beside the step directories rather than inside them on purpose: `make synth`
and `make pnr` both end in `_save_run`, which does `rm -rf` on the step
directory, so a log written inside would be deleted while still being written.
(The `logs/` you see inside `1_synth/` and `7_pnr/` is a different thing —
LibreLane's own `flow.log` and `resolved.json`, copied there by `_save_run`.)

## coherence.json

Each step records when it finished, the knobs it ran with, and a digest of
every file it consumed and produced. A step is **stale** when an upstream step
finished after it did, or when a file it consumed or produced no longer hashes
to what it hashed at the time — either way the chip you would tape out is not
the chip these directories describe.

Two details that decide whether the warnings are worth reading:

- **Staleness is transitive.** Re-running synthesis marks step 6 stale even
  though step 6's direct input (step 5) has not moved, because the layouts
  were drawn for a netlist that no longer exists.
- **Digests hash file content, not mtimes.** A branch switch, a `git stash
  pop` or an editor save-without-change moves mtimes without changing
  anything, and a flow that cries stale at those is one whose warnings get
  ignored.

```
./flow.py status
```

prints the table, one row per step:

| State | Meaning |
| ----- | ------- |
| `OK` | ran, and still describes what is on disk |
| `STALE` | an input moved, or an upstream step re-ran after it |
| `WAITING` | ran, but needs something from you — step 6 with an undrawn cell |
| `FAILED` | the last run failed |
| `MISSING` | never run |

The flow warns and runs anyway: re-running one step in isolation is the normal
way to work here, so the warning is the point, not a gate. `--force` silences
it. `./flow.py status` exits 1 when anything is stale, so a script can gate on
it.

The file's `version` field guards the digest format. Records written by an
older handler are discarded rather than reported as spurious staleness.
