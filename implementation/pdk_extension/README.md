# PDK extension cells

Cells that are **designed**, not mined. The nine-step flow finds recurring
subgraphs in a synthesized netlist and merges them; the cells here exist for
the opposite reason — the PDK's own implementation of a function is not the
best one available, and a hand design beats it.

`AION_mux2i_1` is the first: IHP builds `mux2` the only way complementary
CMOS can (select inverter, AOI22 core, output inverter — 12 devices), and a
pair of transmission gates does the same selection in 4. XOR, XNOR and MUX
are **39% of `tt_um_aion`'s standard-cell area**, and they are exactly the
functions static CMOS is worst at.

| cell | function | devices | sites | PDK equivalent | saving |
|---|---|---|---|---|---|
| `AION_mux2i_1` | `!(S ? A1 : A0)` | 8 | 7 | `mux2_1` + `inv_1`, 13 | 46% |
| `AION_mux2i_2` | same, drive 2 | 8 | 8 | `mux2_1` + `inv_2`, 14 | 43% |
| `AION_mux4i_1` | `!(4:1 mux)` | 18 | 16 | `mux4_1` + `inv_1`, 24 | 33% |

All three are inverting, and not by accident: a transmission gate steers its
input straight through, so the restoring stage that makes the cell modelable
is necessarily an inverter and a second one to undo the polarity costs
CoreSites for nothing electrical. The PDK has no inverting mux at any width,
so each of these competes with a PDK mux *plus* an inverter — which is what
the mapper builds today when the surrounding logic wants the complement.

Until `post-layout` publishes a measured `.lib`, sites are the floorplan
estimate in each cell's `FLOORPLAN.md`, and that is the number ABC chooses on.

```
implementation/pdk_extension/
  <CELL>/
    <CELL>.v                 gold gate-level reference -- what it must compute
    <CELL>.spice             the hand-designed transistor implementation
    <CELL>.provisional.lib   Liberty for the mapper, before the cell is drawn
    FLOORPLAN.md             the placement/routing plan for the layout stage
    ---- everything below is published by post-layout  (git-ignored) ----
    <CELL>.lef  .lib  .gds   the views `make pnr` and `merge_lib.py` read
    <CELL>.cdl               the netlist view
    <CELL>.layout.v          the exporter's generated model
    <CELL>.png               the drawn cell, rendered
  pdk_extension.core         FuseSoC handle on the <CELL>.v models, so the
                             post-synthesis simulations can read them
  pdk_extension_cells.core   FuseSoC handle on the <CELL>.layout.v models,
                             which is what the post-PnR simulation needs
                             instead. GENERATED by scripts/pdk_ext_core.py.
```

One directory per cell, sources and views together — the same shape step 6
of the main flow publishes the mined cells in under `implementation/cells/`.
The two names the exporter cannot have are `<CELL>.v` and `<CELL>.spice`:
those are the design. Its own model is published as `<CELL>.layout.v`, and
its copy of the netlist is not published at all, because the source is the
view.

## Building one

```bash
docker start iic-osic-tools_shell_uid_1000
scripts/pdk_cell.py AION_mux2i_1                 # all three stages
scripts/pdk_cell.py AION_mux2i_1 --from layout   # resume at the layout stage
scripts/pdk_cell.py AION_mux2i_1 --draw manual   # scaffold the generator, stop
scripts/pdk_cell.py AION_mux2i_1 --dry-run       # print commands, run none

scripts/pdk_cell.py AION_mux2i_1 --driver-cell sg13g2_buf_2    # see below
```

### `--driver-cell` is not optional here

The default stimulus is an ideal linear ramp, i.e. a **zero-impedance
driver**. For a static CMOS cell that is a fair idealisation — the input is a
transistor gate, the capacitance isolates, and the driver's job ends with the
waveform it produced. For every cell in this directory it is not: a
transmission gate's input is a source/drain, so the driver stays in series with
the channel for the whole transition, and two drivers of equal slew but
different impedance give different delays. NLDM has no axis for that, which
means the ramp flatters these cells by exactly the effect their Liberty cannot
express.

`--driver-cell` swaps in a real cell, the way vendor libraries are
characterized. It applies to the **post-layout stage only** — the
`characterize` stage is a functional 3-way proof over input vectors and has no
timing in it to flatter — and it is passed to the candidate *and* the abutted
PDK baseline, because a delay measured against a real driver and one measured
against a ramp are not the same quantity and comparing them would be rigged.

**The driver must be non-inverting.** `aion_char` feeds it a ramp that always
rises first and derives the expected output edge from the cell's own unateness;
nothing accounts for a driver that flips the pin. An inverting one inverts every
expected level and the run dies mid-characterization as

```
arc_..._I2_O0_p0_s0_a.spice: the output still had not settled ...
  load 1e-15 F, window a: 5.546e-08 V, wanted ~1.2 V
```

which is not a settling problem at all — the output settled to the *opposite*
rail, at 1 fF, where nothing is too slow. So use a buffer:
`--driver-input`/`--driver-output` default to `A`/`X`, which is any
`sg13g2_buf_*`. A wrong pin *name* is refused against the real `.subckt`; a
wrong pin *polarity* is not, which is why this paragraph exists.

Without the flag, `post-layout` says so:

```
! no --driver-cell: the Liberty will be measured against an ideal ramp,
  which over-states any cell with a pass gate on an input path
```

### `--pex-mode` defaults to 2 here, and to 3 everywhere else

`aion_layout`'s own default is **mode 3, full RC**, and for a mined cell that is
right: wire resistance inside a hand-drawn cell is exactly what a small layout
gets wrong. The cells in *this* directory default to **mode 2, C-coupled**
(`PEX_MODE_DEFAULT` in `scripts/pdk_cell.py`), for two reasons that are specific
to how they are graded.

**Mode 3 can silently break the abutted baseline.** It is the only mode that
runs Magic's `extresist`, which splits a resistive net into renamed segments
(`VSS` becomes `VSS.t0`, `VSS.n1`, …) and can finish having bound the `.subckt`
port to none of them. The rail is then floating: every pull-down is
disconnected, and the extracted cell drives its output to one rail on every
input vector. **LVS does not catch it** — LVS extracts without resistance, where
the net is whole — so the layout is correct and verified while the netlist taken
from it is not, and the damage surfaces as a Liberty file measuring a broken
circuit.

Every cell here is measured against an *abutted PDK baseline*, and an abutted
row of shipped cells is precisely the geometry that trips it. It is luck, not
correctness:

| baseline | width | port bound? |
|---|---|---|
| `AION_mux2i_1` → `mux2_1` + `inv_1` | 13 sites | yes — `R9 VSS.t3 VSS 1.85276` |
| `AION_mux2i_2` → `mux2_1` + `inv_2` | 14 sites | **no** — no resistor names `VSS` at all |

Those two rails are otherwise the same network, resistance for resistance. One
line is missing from the second, and it is the one connecting the cell to
ground. `run_pex` refuses such a netlist by name rather than characterizing it —
but on mode 3, whether a cell can be characterized at all would depend on how
Magic happened to cut a rail.

**And rail resistance is the parasitic these cells least want modelled.** In the
characterization deck the rail port is tied to ideal ground; in silicon the rail
is strapped by the power grid along its whole length and abuts its neighbours on
both sides. Feeding ground in at a single label point through up to 474 Ω of
rail is arguably *less* physical than no rail resistance at all — vendor
libraries characterize with ideal rails.

What mode 2 gives up is signal-net wire resistance, which is real. `--pex-mode 3`
gets it back on a cell whose baseline extracts cleanly:

```bash
scripts/pdk_cell.py AION_mux2i_1 --driver-cell sg13g2_buf_2 --pex-mode 3
```

Do that for the whole library or not at all. **Two cells extracted at different
modes are not comparable, and they land in one merged Liberty** — `merge_lib.py`
splices them into a single `library (...)` block and the mapper chooses between
them on those numbers.

What is never the answer is raising the `extresist` threshold until the port
comes back. Past the rail's own resistance that drops every `R` element from the
netlist and turns full RC into C-only under a `_pex3` file name — the same loss,
unlabelled.

| stage | what it proves |
|---|---|
| `characterize` | ngspice runs **gold, reference and custom** over every input vector and they agree. Gold is the truth table read out of the PDK Liberty, reference is the PDK cell's own transistors, custom is `<CELL>.spice`. A 2-way pass would only say the PDK agrees with itself. |
| `layout` | the GDS built from the cell generator is Magic- and KLayout-DRC clean and LVS-clean against that same SPICE. The generator is the one authored artifact here; `--draw auto` has an agent write it, but the verdict is always the host-side `RESULT:` line. |
| `post-layout` | Magic PEX, the abutted PDK baseline, Liberty characterized from the *extracted* netlist, the area/delay comparison and the view export. Every number is measured from the drawn cell. |

The cell is designed by hand; its *drawing* need not be. The layout stage
takes the same two contracts step 6 of the main flow does:

* `--draw auto` (default) scaffolds `aion_layout_claude/cells/<CELL>.py` if it
  is missing, then loops verify → evidence → `claude -p` until the layout
  verifies or `--max-iters` turns are spent. The agent may write only that one
  file; DRC and LVS run here, on the host, and a turn that leaves the generator
  untouched twice in a row stops the loop — that is an agent that is not
  running, not a layout that is hard.
* `--draw manual` scaffolds it and stops; you finish it by hand and re-run.

Never let the agent touch `<CELL>.spice`: the netlist is the hand design, it
has already been proven against the PDK reference, and it is what LVS grades
the drawing against.

## Getting the mapper to use it

**`EXTRA_LIBS` will not do it.** LibreLane reads those with
`read_liberty -lib -ignore_miss_dir -setattr blackbox`
(`librelane/steps/yosys.py:148`), which registers the cell for STA and
hierarchy and hides it from the technology mapper. `--cells-dir`, which is
how `make pnr` wires the mined AION cells in, goes down that same path.

The list ABC actually maps against is `CELL_LIBS` (deprecated alias `LIB`),
read at `librelane/steps/pyosys.py:296`. So the cell has to be **merged into
the standard-cell Liberty that variable points at** — the PDK's cells plus
this one, in a single `library (...) { ... }` block. Concatenating two `.lib`
files does *not* do that: it produces two library blocks and yosys reads the
first and ignores the rest, without saying so.

```bash
make pdk_ext_lib                       # -> flow/pdk_extension/
make pdk_ext_lib MERGE_LIB_ARGS=--provisional   # before the cell is drawn
scripts/merge_lib.py --corner typ_1p20V_25C     # one corner, by hand
```

It splices each extension cell's `cell (...) { ... }` block inside the base
library's closing brace, carries across any lookup-table template the base
does not already define, refuses on a name collision, and prefers a
characterized `.lib` over a provisional one so a stale estimate cannot
quietly outrank a measurement — `<CELL>/<CELL>.lib` is the measurement, and
it only exists once `post-layout` has published it.

### And the miner needs the same library in its own format

`aion_opt` — flow steps 2 and 3 — does not read Liberty. It reads a JSON
*technology dictionary*, `aion_flow/tech/tech_dict/sg13g2_stdcell.json`, a
flat `{name: {area, pins, function}}`. That file is load-bearing in a way its
name does not suggest, because `load_yosys_json()` **drops every instance
whose cell type is not in it**:

```python
if cell_lib is not None and cell_type not in cell_lib:
    # Skip blackboxes / macros not present in the tech dictionary.
    continue
```

Right for a macro; catastrophic for a standard cell. Once the mapper has used
an extension cell, step 3 reads a netlist holding 698 `AION_mux2i_1` and
writes one holding none — their output nets left undriven, nothing said. The
netlist still elaborates and every gate-level simulation of it then fails on
values that look like logic bugs. (A blackbox's Yosys JSON carries no
`port_directions` either, so the dictionary is also the only thing that can
tell aion_opt which pin of the cell is its output.)

`make pdk_ext_lib` therefore writes a second file, and writes it **from the
merged typ Liberty** rather than from the cells' own `.lib`s — the one file
that says what the mapper actually chose from is the one the miner has to
agree with:

```
flow/pdk_extension/lib/sg13g2_stdcell_aion_<corner>.lib   ABC, OpenSTA, the LEC
flow/pdk_extension/tech_dict/sg13g2_stdcell_aion.json     aion_opt
```

```bash
scripts/merge_tech_dict.py                      # just the dictionary
```

The Boolean function is copied across verbatim — the dictionary and Liberty
use the same expression syntax (`!I2*!I0+I2*!I1`), so this is a transcription,
not a translation. Existing entries are never touched: the base dictionary is
the PDK's own description of its cells.

**The miner can now mine patterns that contain an extension cell.** At
`ELITE_COUNT=2` it does not — the top of the cover is unchanged — but raising
it, or `REWRITE_CELLS=all`, will eventually select one, and a mined cell built
on an `AION_mux2i_1` has no `.subckt` in the PDK's `sg13g2_stdcell.spice` for
step 4's reference leg to find. Steps 5 and 6 work from the cell's function
and are unaffected.

### It is already wired in

`make synth` — and so step 1 of the main flow — runs `make pdk_ext_lib`
first and points `CELL_LIBS` at the result, so the mapper sees these cells
without anything further being done. `make pnr_simple` does not, on purpose:
that target is the PDK-only baseline every later comparison is measured
against, and an extension cell in it would move the baseline along with the
result.

Three knobs and two consequences:

* `make synth PDK_EXT=0`, or `./flow.py 1 --set PDK_EXT=0`, maps against the
  plain PDK library. Everything else is unchanged.
* `MERGE_LIB_ARGS=--provisional` lets a cell that has not been drawn yet into
  the library, on its floorplan estimate. `make pdk_ext_lib` is strict by
  default.
* `PDK_EXT_CORNERS` in the Makefile lists the corners the library is built
  for, and it has to cover every corner in the PDK's `STA_CORNERS`.
  `CELL_LIBS` is *replaced*, not merged into the PDK's, so a corner left out
  has no Liberty at all and OpenSTA cannot link a netlist at it.

  The cells are characterized at **typ** only, so `merge_lib.py` splices the
  same typ tables into the fast and slow libraries. That is honest enough for
  the pre-PnR sanity STA step 1 runs and is **not** something to sign off
  against; characterize the cell at the other two corners before it matters.

* `implementation/pdk_extension/` is one of step 1's recorded inputs, so
  adding or recharacterizing a cell here marks the synthesis — and everything
  downstream of it — STALE rather than letting a later step stand on a
  netlist mapped against a different cell library.
* Steps 2 and 3 pass the extended **technology dictionary** to `aion_opt` as
  `CELL_LIB`, and step 3 points the **LEC** at the extended Liberty. Both are
  spliced on demand by `scripts/flow/pdk_ext.py` when they are not on disk, so
  a step run on its own after a `make clean` still reads a library that
  describes its own netlist. `PDK_EXT=0` leaves both at their stock defaults.
* The netlist can now instantiate an extension cell, so the gate-level
  simulations need a model for it. `pdk_extension.core` carries the gold
  `<CELL>.v` views and `aion.core`'s `post_synth_sim*` targets pull it in.
  **Adding a cell means adding a line there too.**

## Getting PnR to place it

Different problem, different variable. `make pnr` hardens a netlist that
already names the cell, so nothing is mapped any more and the question is
only whether LibreLane has its views:

```bash
make pnr PDK_EXT=0     # harden without them (a netlist that names one will fail)
```

`--pdk-ext-dir` is a **separate flag** from `--cells-dir`, and not because the
cells are treated differently — both end up in the same `EXTRA_LEFS`,
`EXTRA_LIBS`, `EXTRA_GDS`, `EXTRA_VERILOG_MODELS`, `EXTRA_SPICE_MODELS` and
`EXTRA_CDLS`. It is separate because the two directories *name* their views
differently. Under `implementation/cells/` a cell is every file sharing one
stem, which works because step 6 publishes nothing else there. Here the
sources sit beside the views, and three names would group wrong:

| file | what stem grouping would do | what it is |
|---|---|---|
| `<CELL>.v` | the cell's Verilog model | the **structural** gold reference — a PDK mux2 and inverter. Right for the post-synthesis simulation, wrong for PnR. |
| `<CELL>.layout.v` | a cell named `<CELL>.layout`, Verilog only, no LEF | the model PnR and the SDF need |
| `<CELL>.provisional.lib` | a cell named `<CELL>.provisional`, Liberty only | a floorplan **estimate**. A run timed against one is not a result. |

So `collect_cells.PDK_EXT_VIEW_SUFFIX` names each view instead of inferring
it, and a cell with no `<CELL>.lef` is simply not offered to PnR — which is
the truth about a cell nobody has drawn.

### A drawn cell also has to be *reachable*

`RT_MIN_LAYER` is `Metal2`, so the router never puts a wire on Metal1 and
every pin is entered through a Via1. The Metal2 pad of that via is a Metal2
shape like any other and must keep 0.21 µm from every other net's Metal2 —
**the cell's own risers included**. A port can be wide enough, on-track and
unobstructed and still admit no via.

`AION_mux2i_1/I2` and `AION_mux2i_2/I2` are exactly that: 280 nm gate pads
with the cell's own `Sb`, `m` and `I1` Metal2 risers 15 nm to one side. PnR
places all 698 instances, routes globally, and then aborts:

```
[ERROR DRT-0073] No access point for _07163_/I2 (AION_mux2i_1)
```

once per *orientation*, not per instance — four errors for 698 placements,
which reads like bad luck and is not. `scripts/collect_cells.py` checks this
in about a second now and refuses to start PnR; all 283 signal pins of the
shipped sg13g2 library pass it, and so do both mined AION cells. Widening the
Metal1 port does not help on its own — see `AION_mux2i_1/FLOORPLAN.md` §9.

### `EXTRA_LIBS` here, `CELL_LIBS` at synthesis

The exact opposite of the section above, and both are right. Synthesis has to
offer the cell to ABC, and only `CELL_LIBS` reaches the mapper. PnR maps
nothing — the netlist is fixed and `--from Checker.NetlistAssignStatements`
skips synthesis outright — so all the Liberty has to do is let OpenSTA link
and time the instances, which is what `EXTRA_LIBS` is for. Putting the cells
in both would define each of them twice, and replacing `CELL_LIBS` here would
leave `make pnr` and `make pnr_simple` timed against differently-built
libraries: the substitution has to be the only variable between them, or step
9's comparison is measuring two things at once.

### Two Verilog views, and the simulation has to pick

`<CELL>.v` is structural and `<CELL>.layout.v` is a leaf model with a specify
block, and which one a gate-level run wants depends on where it is:

```
post_synth_sim, post_synth_sim_ai   <CELL>.v         pdk_extension.core
post_pnr_sim_ai                     <CELL>.layout.v  pdk_extension_cells.core
```

After PnR the cell is a **leaf** — LibreLane hardened it as a macro and the
SDF carries one `CELL` entry per instance — so the structural view would
describe a hierarchy the netlist and the SDF do not have, and every `IOPATH`
record for the cell would annotate nothing. Reading both is worse: each
defines the same module.

`pdk_extension_cells.core` is **generated**, unlike its hand-kept sibling, for
one reason: `<CELL>.layout.v` does not exist until the cell has been drawn,
and a FuseSoC fileset naming a file that is not there fails every target that
depends on it — including targets with nothing to do with these cells. So it
is rebuilt from what is on disk, with the same placeholder flow step 6 uses
for the mined cells:

```bash
make pdk_ext_lib             # regenerates it, along with the Liberty and the dict
scripts/pdk_ext_core.py      # just this one
```

Verified on a 32-bit 2:1 mux:

```
PDK-only:   32  580.608   sg13g2_mux2_1
PDK+AION:   32  522.547   AION_mux2i_1     (-10.0%)
```

Nothing was done to force that. No `SYNTH_EXCLUDED_CELL_FILE` entry banning
the PDK mux2, no custom ABC script, no `dont_use` list — ABC compared
`area : 16.3296` against `area : 18.1440` and took the smaller one.

Which makes the Liberty's `area` the load-bearing number in this whole
exercise. It is currently a floorplan estimate, and if the drawn cell comes
out bigger then ABC will have made that choice on a number that was wrong.
Re-run the merge after `post-layout` and the measured `.lib` takes over.
